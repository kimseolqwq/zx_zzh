# 基于多本地大模型融合的手机购买推荐系统——项目报告

## 摘要

“择机”是一个面向中国大陆消费者的手机购买推荐 Web 系统。系统以 SQLite 保存手机型号、内存版本、官方旗舰店商品和价格快照，以品牌官网与人工留证的电商页面作为事实来源，并调用 Qwen3 1.7B、Qwen2.5 1.5B、Gemma3 1B 三个本地模型进行多视角评分。最终结果不是简单拼接模型回答，而是通过“硬约束筛选 + 五维加权融合 + 分歧惩罚”产生，并展示价格来源、模型投票、置信度、分项贡献和证据链。

截至 2026-09-16，数据库包含 10 个品牌、203 款在售机型和 394 个内存版本。本机保存 817 个原始证据文件，约 136.9 MB；90 款手机具有通过质量规则的官网产品图。3 个电商商品完成店铺、SKU、链接和证据核验，共保留 4 个真实价格快照，其中 1 个为最近 7 天新鲜快照。未核验价格不进入推荐最低价，缺失字段保持为空。

## 1. 需求与范围

系统支持用户输入预算、主要用途、偏好品牌和最低存储容量，返回最多 5 个满足条件的具体内存版本。用途分为摄影创作、重度游戏、轻薄续航和综合体验。推荐卡片展示三个平台的价格位置；已有核验商品时直达商品页，否则只提供带型号和版本关键词的平台搜索入口并标注“尚未核验”。国补与百亿补贴只按页面实显值保存，资格由用户在结算页确认。

管理员通过账号登录后维护品牌、型号、版本、平台商品和价格快照。系统使用 Argon2 哈希密码、CSRF 防护、登录限流和审计日志，普通访问者不能修改数据库。

## 2. 系统架构

系统分为四层：

1. 数据采集层：品牌官网低频采集器、离线证据重解析器、电商人工核验导入器；
2. 数据层：SQLite + SQLAlchemy，保存结构化实体、来源、采集时间和历史价格；
3. 智能服务层：硬约束候选过滤、Ollama 三模型调用、JSON 校验、失败降级、融合排序；
4. 展示层：FastAPI + Jinja2 Web 页面，包括智能推荐、手机库、详情页、系统评估和管理员 CRUD。

## 3. 数据库设计

核心表包括：`brands`、`phone_models`、`phone_variants`、`platform_listings`、`price_snapshots`、`users`、`audit_logs`、`recommendation_runs`、`model_runs` 和 `crawl_logs`。

型号与内存版本是一对多关系，内存版本与平台商品是一对多关系，平台商品与价格快照也是一对多关系。这样既能表示同一手机的 12GB+256GB、16GB+512GB 等版本，也能保留京东、天猫、拼多多随时间变化的价格历史。唯一约束防止同品牌机型、同内存组合和同平台 SKU 重复入库。

## 4. 数据采集与可信度控制

当前目录覆盖 203 个官网在售条目，其中 145 款具有可离线重解析的成功页面证据。采集器先检查 `robots.txt`，按域名限速，保存 HTML、可见文本、URL、时间和哈希，然后只提取明确标注的 CPU、屏幕、相机、电池、重量和内存版本。解析器支持 RAM+ROM 明确组合、仅列存储容量、同一 RAM 对应多个 ROM；不会对不明确的 RAM/ROM 列表做笛卡尔积。离线重解析会合并全部历史采集报告并为每款手机选择最新成功证据，不因后续定向小报告丢失旧数据。

电商数据采用“浏览器查看—截图/文本留证—CSV 审核—校验入库”流程。导入器检查平台域名、“平台 + 品牌 + 精确店名”白名单、具体 SKU、审核人、价格范围和证据文件；同一批数据重复导入不会新增重复快照。自动解析只生成 `needs_review` 候选，证据审核门禁再次核对店铺、型号和内存版本。当前真实价格样本仍少，这是项目已知限制，不能用模拟价格填充。

当前核心字段覆盖率：CPU 52.2%、屏幕尺寸 49.3%、刷新率 48.8%、主摄 50.7%、电池 52.2%、重量 50.2%、可信官网产品图 44.3%、来源 URL 100%。Logo、导航缩略图和页脚素材不计为产品图。仍有 144 款缺至少一个推荐关键参数、77 款动态官网页面未解析出明确版本、173 款缺官网明确发布日期，均进入缺口队列。

## 5. 推荐与融合算法

第一步在数据库中执行硬约束：在售、版本有效、存储容量不低于要求、品牌匹配、无资格公开价不超过预算。国补价不参与默认预算判断，避免把无资格用户无法获得的价格当成可买价格。

第二步让三个模型仅依据候选数据输出 JSON 排名。系统截断非法分数，忽略不存在的版本 ID，并记录模型延迟、token 数、输出速度、JSON 是否可解析和错误信息。

第三步计算五维分数：

- 需求匹配 35%；
- 模型共识 25%；
- 数据可信度 20%；
- 性价比 15%；
- 价格时效性 5%。

模型共识分为模型平均分乘以一致性系数。一致性系数随评分标准差增大而降低，最低为 0.7。若所有模型失效，系统用规则分降级，仍可返回满足硬约束的结果。页面同时展示五项原始分、权重、贡献分、模型数量与分歧标准差，因此结论可追溯。

## 6. 实验设计与结果

固定基准包含 30 条查询，其中 23 条有候选、7 条预期无结果。预算覆盖 500–7000 元，包含四种用途、品牌约束、256/512GB/1TB 存储和预算边界。历史离线实验对比四种方法：仅规则、单 Qwen、三模型融合、去除模型共识。

四种方法的硬约束正确率和有/无结果判定正确率均为 100%。仅规则、单 Qwen、去共识与融合 Top1 的一致率分别为 95.7%、82.6%、95.7%，表明三模型融合会实质改变部分排序，但主观有用性是否更好仍需人工盲评。

上述 30 条实验使用早期 8B/7B/4B 配置，23×3=69 次模型调用的原始结果仍保留在 `outputs/benchmark/`，用于说明模型缩小前的性能瓶颈，不能冒充当前在线配置性能。

当前在线配置使用 Qwen3 1.7B、Qwen2.5 1.5B、Gemma3 1B。`run.ps1` 在启动 Web 服务前按真实 2048 上下文并行预热；预热不计入用户请求时间，也不改变模型数量、候选数、融合权重或输出质量约束。2026-09-16 的四类在线实测延迟分别为 1.27、3.02、1.32、2.82 秒，全部低于 10 秒；每次均返回 3 个结果，并且每个结果都有 3 个有效模型投票。

自动化测试共 40 项，覆盖页面、权限、CSRF、官网与价格解析、图片质量、官方店白名单、证据路径、幂等导入、SQLite 检查点、严格预算/品牌约束、三模型融合和交互结果结构。

## 7. 页面与交互

手机库按品牌分组，支持品牌统计、关键词查询、排序和详情跳转。详情页展示 CPU、尺寸、刷新率、像素、电池、重量、版本和来源。推荐结果默认展开 Top1；鼠标悬停或键盘聚焦 Top2/Top3 时，对应卡片动态展开。三个平台分别显示价格、促销类型、核验时间和是否过期。

公开系统评估页实时读取数据库与运行日志，不使用写死的演示数字。管理员后台负责增删改查，页面修改会留下审计记录。

## 8. 局限与后续工作

主要限制是电商价格核验需要登录态、地区与 SKU 选择，自动化又不能绕过验证码，因此当前三平台覆盖率低。本轮实测京东搜索返回访问频繁、天猫出现滑块、拼多多出现验证码；这些任务均记录为 `blocked`。下一阶段应在专用浏览器人工完成验证后，按 1182 条优先队列先补主流版本，再扩充其他版本；大促期间应缩短更新周期。

第二个限制是部分官网使用动态渲染或不明确标注发布日期，系统选择留空并进入缺口队列。第三个限制是冷启动会产生模型加载开销；系统已把该开销前移到服务启动阶段，并在请求阶段并行调用三个轻量模型，同时保留超时降级以保证页面可用。

## 9. 结论

本项目完成了可运行的 Web 系统、关系型数据库 CRUD、本地多模型调用、可解释融合、来源留证和性能度量。项目的关键价值不在于“同时问三个模型”，而在于把事实、语义判断、约束决策和审计度量分开：数据库提供可验证事实，模型提供多视角判断，算法保证硬约束与最终排序，日志与证据支持解释和复现。
